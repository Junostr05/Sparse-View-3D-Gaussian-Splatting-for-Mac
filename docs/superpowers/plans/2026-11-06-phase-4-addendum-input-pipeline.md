# Phase 4 addendum — input pipeline decisions (user interview, 2026-11-06)

This addendum amends `2026-11-06-phase-4-sparse-view-quality.md` (written before these answers). Where they disagree, **this file wins**. Decisions come from the `grill-me` interview with the user.

## Decisions

| # | Topic | Decision |
|---|---|---|
| A1 | Inputs | **Both** video files **and** folders of photos (single iPhone photos included). The user must be able to drop in a folder of images or a video. Per-frame depth maps are generated by the depth model; ground-truth/LiDAR depth stays optional. |
| A2 | Frame selection (video) | **Automatic with manual correction.** The app proposes N frames (spread over the camera motion, preferring sharp frames), shows them in a strip, and lets the user swap/remove frames. **N is a user setting, default 6.** **Users can also choose "use all frames"** (`FrameSelectionMode.all`, user request 2026-11-06): every candidate frame is used, no selection. For videos the candidate sampling interval is a setting too (default 0.25 s; "every frame" allowed); the UI warns when the number of frames makes training slow or memory-heavy (rough guard at ~100 views, see `TrainingMemoryBudget.reservedImageBytes`). Photo folders default to "all photos". |
| A3 | Camera poses | **Several ways, in this order:** (1) bundled COLMAP, (2) Apple Photogrammetry (`PhotogrammetrySession` poses/point cloud), (3) a foundation model (DUSt3R/MASt3R-style, optional non-commercial download; this pulls Phase 6 forward). Already-posed inputs (COLMAP folder, ARKit capture) keep working and skip this stage. |
| A4 | COLMAP delivery | **Keep the App Sandbox; bundle COLMAP** as a helper started through an XPC service (not Homebrew). Consequences below. |
| A5 | Depth model | **Depth Anything V2 Small, downloaded on first use** (Apple's Core ML conversion published on Hugging Face — package name, I/O format and license must be **verified on a Mac**; the cloud container cannot fetch it). Checksum-pinned download into the app's container; needs `com.apple.security.network.client`. Offline or download failed → depth features stay off with a clear notice (training still works). |
| A6 | Quality metric | **SSIM + PSNR** on the held-out view; LPIPS is a later option. |
| A7 | Time budget | **Three presets: Fast / Standard / Quality**, each setting image size, iterations, regularizer strength and early stopping together (Fast ≈ 640 px / few iterations, Standard ≈ 1000 px, Quality up to 1600 px / 15 000+ iterations). Individual values stay editable. |
| A8 | Video in the project | Store **only the selected frames** (PNG in `images/`) plus provenance (source file name, timestamp per frame). The original video is not copied. Frame selection can only be redone while the user still has the video. |
| A9 | Order of work | **Input pipeline first**, then the quality features of the main Phase 4 plan. |
| A10 | Test data | The user will send a few example photos as a zip in the chat; they are used as real-data fixtures (small, downscaled) and for manual evaluation. |

## Consequences and risks to settle early

1. **Bundled COLMAP under the sandbox is the most expensive item.** Needs: a reproducible macOS arm64 build (CMake, Eigen, Ceres, Boost, SQLite, glog/gflags, FLANN, METIS, CGAL optional; CPU-only SIFT), code signing and notarization of every binary and dylib, an XPC helper with inherited sandbox that can read the user-chosen image folder and write the project, progress reporting and cancellation. **First task is a feasibility spike on CI** (what `brew install colmap` pulls in, size, licenses of the dependency closure, whether a headless sparse reconstruction runs on the runner) before any app work.
2. **Licensing of the bundled closure must be checked before shipping.** COLMAP itself is BSD-3; some dependencies historically were not permissive (e.g. FreeImage is GPL/FIPL). The repository is Apache-2.0 and the CLAUDE.md rule only allows commercially usable components in the bundle. If the closure is not clean, fall back to COLMAP-as-optional-download (still sandbox-compatible if the user places the binary) or lean harder on stage 2/3 of A3.
3. **COLMAP often fails with 3-6 views.** That is why A3 lists fallbacks; each stage reports success/failure with the reason, and the app falls through to the next stage automatically or by user choice.
4. **Apple Photogrammetry** needs macOS 12+ and typically more than 3-6 images; treat as best effort.
5. **Sandbox entitlements to add:** `com.apple.security.network.client` (model download), possibly `com.apple.security.files.user-selected.read-write` (already present) plus a security-scoped bookmark if a source folder/video must be re-read later.

## New tasks (to be inserted before the quality tasks of the main plan)

All use the same task rules as the Phase 3 plan (Haiku implements, Sonnet reviews, macOS tasks verified by CI, Xcode type-checker rule applies). Numbers are prefixed `P` to keep them apart from the main plan's 1-22.

- **P1 Frame selection core** (SplatCore, Linux-testable): `FrameSharpness` (variance of the Laplacian on `RGBImage`), `FrameSelector.select(candidates:count:)` that spreads `count` frames over the timeline preferring sharper candidates (segment the timeline into `count` bins, take the sharpest per bin, enforce a minimum spacing). Tests with synthetic blur levels and timestamps.
- **P2 Video frame extractor + photo folder import** (macOS-only; honours `FrameSelectionMode` incl. `.all` and the sampling-interval setting): AVFoundation (`AVAssetImageGenerator`/`AVAssetReader`) samples candidate frames (e.g. every 0.25 s, capped), downscales, scores via P1; ImageIO reads photo folders (EXIF orientation applied, size normalised). Output: `[CapturedFrame]` (image data, source name, timestamp).
- **P3 Project provenance** (SplatIO, Linux-testable): manifest additions for source kind (`video`, `photos`, `colmap`, `arkit`), per-frame provenance, Phase 3 projects still load (version bump handled by the existing `formatVersion` rules).
- **P4 Pose provider protocol and stage plumbing** (SplatCore/SplatIO, Linux-testable): `PoseProvider` returning poses + intrinsics + optional sparse points for a set of frames, `PoseEstimationResult`/failure reasons, fallback chain, mapping into the existing COLMAP-style `TrainingDataset` path.
- **P5 COLMAP feasibility spike** (CI workflow + report): see risk 1 and 2; output is a written report in `docs/` with a go/no-go.
- **P6 Bundled COLMAP helper + XPC** (macOS, only after a P5 "go"; Opus review).
- **P7 Apple Photogrammetry provider** (macOS-only).
- **P8 Model downloader** (macOS-only, Linux-testable checksum/path logic split out): download, verify SHA-256, store, load; offline behaviour.
- **P9 Pipeline UI** (app): import entry points (video / photo folder / COLMAP / ARKit), frame strip with swap/remove, frame-count setting (default 6), step list Frames → Poses → Depth → Train with per-step status, the three presets (A7).

The main plan's Task 20 (SplatDepth/Core ML) now loads the model from P8's location instead of bundling it; its Task 22 (app) is merged with P9.

## Real-data findings (2026-11-06, user photos)

- The user's 13 iPhone 15 Pro photos of a glass/brass coffee table (HEIC, 4284x5712, portrait, GPS in EXIF) were reduced to 900x1200 JPEG (EXIF stripped) and run through **pycolmap 4.2.1 on CPU (Linux)**: SIMPLE_RADIAL, single camera, **all 13 images registered in ~13 s, 1448 points, mean reprojection error 0.52 px.** So the COLMAP pose stage works on this kind of scene even with glass and reflections (floor texture and a QR-code coaster give plenty of features).
- COLMAP 4.x additionally writes `rigs.bin` and `frames.bin`; `cameras.bin`, `images.bin` and `points3D.bin` keep the legacy layout (verified: poses equal pycolmap's, files parse to the last byte). The existing `COLMAPReader` needs no change; Swift loader + initialization + CPU trainer ran on the dataset (13 views, 1448 points, finite loss).
- The **HEIC** input format must be supported by the photo-folder import (ImageIO reads HEIC on macOS) and **EXIF orientation must be applied**; iPhone photos are 12-48 MP, so downscaling to the preset's maximum side is mandatory before COLMAP and training.

## P5 result — COLMAP feasibility spike on CI (2026-11-06, run 42226371882)

**Verdict for "copy the Homebrew build into the app": NO-GO.**

- `brew install colmap` (4.2.1, arm64, min macOS 26) works; binary + dependency closure = **235 MB, 217 files, 71 formulas**, no unresolved references.
- **Licenses:** the closure contains copyleft-only components — Qt (`qtbase`, `qtsvg`, GUI), `ffmpeg` (GPL-3.0), `x264`/`x265` (GPL-2.0+), `gettext`, `dbus`, `gcc` runtime, `suite-sparse` (contains GPL modules), `xz`; plus LGPL libraries (`libheif`, `libde265`, `mpfr`, `glib`, `mpg123`, `lame`, `libraw`) and several non-allowlisted permissive ones (libpng, libtiff, IJG, freetype, ICU — these are fine, just not on the spike's allowlist). The GPL parts come from the GUI, video and learned-feature options of the Homebrew formula, not from COLMAP itself (BSD-3).
- **Signing:** Homebrew binaries are ad-hoc signed with no Team ID and carry Homebrew absolute paths; every binary/dylib would have to be re-signed with our identity and relinked (`install_name_tool`) for the app bundle.
- **Headless run: inconclusive.** The synthetic 4-view scene gave only ~200 SIFT features per image and no matches, so the mapper stopped with "No images with matches" and the converters aborted on the empty model (exit 134). This is a test-data problem, not a COLMAP problem — the same COLMAP version registered all 13 real photos with pycolmap.

**Consequence:** bundling is only viable with our own **minimal source build**: `GUI_ENABLED=OFF`, `CUDA_ENABLED=OFF`, no ONNX/learned features, no CGAL, no ffmpeg; Ceres built with Eigen/Accelerate sparse instead of SuiteSparse; static or app-private dylibs with `@rpath`. Next step is a second CI spike that builds this and runs it on a **real-looking** scene (sample photos, not the synthetic sphere), then re-evaluates size and licenses. If that fails, fall back to the pose-provider chain without COLMAP first (Apple Photogrammetry, foundation model) and offer COLMAP only as an optional user-installed tool. The user decision A4 (keep the sandbox, bundle COLMAP) is unchanged.

## COLMAP licence findings from reading the source (2026-11-06, Mac session)

Spike 2 stopped at configure, so these had not surfaced in a build:

- **CHOLMOD is required** by COLMAP 4.2.1 (`find_package(CHOLMOD REQUIRED)`), for one solver class that already falls back to Eigen's `SimplicialLDLT`. Removed by `Tools/ci/patch_colmap_no_cholmod.py`.
- **LSD is AGPL** (`src/thirdparty/LSD`), enabled by default. `LSD_ENABLED=OFF` is mandatory.
- **SiftGPU is non-commercial** (`src/thirdparty/SiftGPU`: "educational, research and non-profit purposes"). It is only built with `GPU_ENABLED`, so `OPENGL_ENABLED=OFF` and `CUDA_ENABLED=OFF` are mandatory.
- **Homebrew's `openimageio` pulls ffmpeg, x264/x265, libheif and libraw**, so OpenImageIO must also come from a minimal source build.

`Tools/ci/colmap_minimal_build.sh` now covers all of these and has a licence gate in its report.

## P8 result: depth model (2026-11-06, verified on a Mac)

- **Source:** Hugging Face `apple/coreml-depth-anything-v2-small`, commit `cfef6f6f`, licence Apache-2.0 (model card, tag and the model's own metadata). Pinned variant `DepthAnythingV2SmallF16.mlpackage`, 49.8 MB.
- **It is a directory of 3 files, not one file and no zip**, so `ModelDescriptor`/`ModelStore` became multi-file. Checksums were computed from the downloaded files; the two LFS files also match Hugging Face's SHA-256.
- **I/O:** input `image` RGB, output `depth` `Grayscale16Half` (`L16Half`), both **fixed at 518x392** (`hasSizeFlexibility: 0`, although the model card suggests flexible sizes).
- **Output semantics:** bright = near, so the values behave like relative inverse depth, normalised (observed 0.10-1.0 on one photo). This matches main plan decision P4; Task 20's rotation for portrait views still applies.
- **Glass:** on the coffee table the glass top reads as a vague surface and the floor below it disappears from the prior. Expect the depth prior to be wrong on glass.
- **Real download** through `URLSessionModelDownloader` works (status `ready`, Core ML compiles and loads it). The first version reported no byte progress, because the async `download(from:delegate:)` does not call `didWriteData`; it now uses a callback download task. Not yet run inside the sandboxed app, since no UI triggers it before P9.

## P7 probe: Apple Photogrammetry on real photos (2026-11-06, one scene only)

`PhotogrammetrySession` `.poses` on the table photos, compared with COLMAP's 13-view camera centres by pairwise distances (invariant to the similarity transform):

| Input | Registered | Time | Correlation | Mean / max rel. error |
|---|---|---|---|---|
| 13 JPEG with EXIF | 13/13 | not recorded | 1.0000 | 0.3 % / 1.0 % |
| 13 PNG, EXIF stripped, oriented | 13/13 | 3.5 s | 1.0000 | 0.2 % / 0.8 % |
| 6 JPEG with EXIF | 6/6 | 2.3 s | 0.9999 | 0.4 % / 1.3 % |
| 6 PNG, EXIF stripped, oriented | 6/6 | 2.2 s | 0.9999 | 0.3 % / 1.0 % |

COLMAP 4.2.1 (CPU) on the same 6 JPEGs registered **5/6** with 175 points, reprojection error 0.46 px.

Notes for building P7:

- This compares camera centres only, not orientations, and says nothing about training quality yet.
- `session.outputs` does not end after `.processingComplete`; the consumer must stop itself.
- `.poses` returns no intrinsics. iPhone 15 Pro EXIF has `FocalLenIn35mmFilm = 35`. Against COLMAP's calibrated `fx = 1201.66` at 1200x900, the diagonal rule `f35 * diagonal_px / 43.27` gives 1213 (+1.0 %), the long-side rule `f35 * width / 36` gives 1167 (-2.9 %). **Use the diagonal rule** and store `f35` in `FrameProvenance` at import, because the import strips EXIF.

## COLMAP delivery: measured, decision pending (user, 2026-11-06)

Measured with an ad-hoc signed test app: inside the App Sandbox a file the app writes gets `com.apple.quarantine`, and starting it fails with `EPERM` from the container and from temp; `/opt/homebrew/bin/colmap` fails the same way. So "download COLMAP on first launch" only works without the sandbox, which would change A4. Not tested with a Developer ID signed app.

**User decision:** build P7 first and measure training quality on a held-out view against COLMAP poses. The sandbox stays, and no further COLMAP delivery work happens until then. A3 and A4 are unchanged for now and get decided again with that data. Options then: drop the sandbox and download, keep the sandbox with COLMAP folder import only, or the bundled XPC helper.

## P7 result: Apple vs COLMAP poses, measured on training quality (2026-11-06)

Setup: the 13 table photos as upright PNGs (EXIF stripped, as the import pipeline produces them), 450x600 after the loader's downsampling. Three views (`IMG_9014`, `IMG_9018`, `IMG_9022`) are held out of training; both pose sets come from all 13 images. 5 000 iterations, Standard preset schedule, SH 1. Metrics on the held-out views: mean PSNR and SSIM (decision A6). Seeds 0, 1, 2; numbers are means over the seeds (sd in brackets).

| Poses and initial points | Held-out PSNR | Held-out SSIM | PSNR on 3 training views |
|---|---|---|---|
| COLMAP + its 1 418 points | **14.76** (0.07) | **0.389** | 32.60 |
| Apple + its 543 points | 14.25 (0.31) | 0.354 | 30.22 |
| COLMAP, random init (single run) | 12.42 | 0.377 | 32.40 |
| Apple, random init (single run) | 12.99 | 0.350 | 30.85 |

Findings:

- COLMAP poses are better on this scene: +0.5 dB / +0.035 SSIM held-out and +2.4 dB on the training views. The gap exceeds the seed spread, but it is **one scene, 13 images, one phone**.
- Apple's poses are usable, not equivalent. The training-view gap suggests small pose or intrinsics errors (Apple returns fx, fy, cx, cy but no distortion model in our import; COLMAP's SIMPLE_RADIAL fit had k1 = 0.02).
- **The initial points matter more than the pose source:** both sources gain 1.3-2.3 dB held-out from any SfM point cloud over random initialisation, and Apple's much sparser cloud (543 points) is already enough for most of it.
- Absolute held-out quality is low for both (about 14-15 dB): 10 training views of a glass table are the sparse-view regime that the rest of Phase 4 addresses (depth prior, dense init, regularizers). Pose errors are not the main limit.
- Apple's pose estimation takes about 3-20 s here; COLMAP needs about 13 s on CPU (CI build: 805 s to build, 14 files, 3.8 MB closure; the licence gate passes).
- Rotation convention: `R_c2w_colmap = R_apple_c2w · diag(1, -1, -1)` (0.27 degrees mean difference to COLMAP).
- Not verified: the colour channel order of Apple's point cloud (`SIMD4<UInt8>`), video input, scenes with less texture, fewer views (6), and Apple without a point cloud.

Consequence for A3/A4 (decision pending, not made here): the built-in Apple provider works and needs no signing, XPC or download, so the app can ship a pose stage without COLMAP. COLMAP stays worth having as the better first stage when it is available. Options: (1) Apple only plus the existing "Import COLMAP…" for users who run COLMAP themselves; (2) drop the sandbox and download our minimal build on first launch (needs the app to run unsandboxed, see the measurements above); (3) the XPC helper as in A4.

## Phase 4 measurements and default decision (2026-11-07, Mac session)

Held-out metrics are the only quality signal used. Two data sets: (a) the synthetic scene of `SparseViewQualityTests` (160x120, 3000 iterations, 1200 sphere Gaussians, 200 SfM points, 4 novel views, Metal training); (b) the 13 table photos with Apple poses, 3 held-out views, 5000 iterations, 2 seeds (the seed spread is about 0.3 dB, so differences below 0.3 dB are noise).

### Depth alignment finding (fixed)

The first benchmark showed dense init and the depth prior *hurting*. Cause: the per-view scale/shift fit of the monocular depth to the SfM points used a median-based fit, which fails when more than half of the SfM points are occluded in a view (half the points are on the far side of the object). Raw depth lay on the surface for 93 % of pixels, the aligned depth for only 40 %. The fit now picks the scale/shift with the largest consensus among the points (tolerance 0.05) and refines only on those inliers; afterwards 95 % lie on the surface and the real photos report "10 of 10 views aligned". Tolerance 0.05 was tuned on one scene (53 inliers against 48 required); a per-view visibility test would be the stronger fix and is not done.

### Synthetic benchmark (after the alignment fix), novel-view PSNR in dB, delta to the Phase 3 baseline

| Views | baseline | dense init | + depth prior | + regularizers | + pseudo-views | all | all + leave-one-out |
|---|---|---|---|---|---|---|---|
| 3 | 25.47 | -1.19 | **+1.62** | +0.68 | -1.22 | -1.24 | -1.36 |
| 4 | 29.10 | -2.07 | -0.67 | -1.84 | -1.57 | -1.69 | -1.57 |
| 6 | 28.47 | +4.07 | **+5.23** | +4.72 | +4.47 | +5.27 | +4.42 |

Axis ratio > 10 drops from 33–46 % of the Gaussians (baseline) to 0–4 %, far floaters are 0 % everywhere. The plan target (every "all" row at least baseline + 1 dB at 3 and 4 views) is **not met**: at 4 views no configuration beats the baseline, and pseudo-views lose 1–3 dB against the depth prior alone at 3 and 4 views. The 6-view result is large because the baseline itself is poor there (random SfM subset), so it says less than it seems.

### Real photos (Apple poses, 3 held-out views, mean of 2 seeds, held-out PSNR / SSIM)

| Configuration | PSNR | SSIM |
|---|---|---|
| none (Phase 3) | 14.20 | 0.343 |
| depth prior + dense init | 14.92 | 0.371 |
| depth + anisotropy | 14.84 | 0.369 |
| depth + anisotropy + isolation pruning | 14.70 | 0.367 |
| depth + anisotropy + isolation + scale cap 0.2 | 14.63 | 0.367 |
| anisotropy only | 14.77 | 0.353 |
| isolation pruning only | 14.02 | 0.324 |
| scale cap only | 13.95 | 0.317 |
| everything (old default) | 14.57 | 0.358 |

The depth prior is the only component with a clear gain (+0.7 dB, +0.028 SSIM). Anisotropy and isolation pruning are neutral next to the depth prior, but they remove needles and floaters. Scale cap and pseudo-views cost quality on both data sets. Leave-one-out costs twice the training time and gave +0.13 dB at 4 views and -0.85 dB at 6 views in the benchmark.

### Decision (user, 2026-11-07): "measured defaults"

Decision 14 changed. New projects start with the depth prior (Pearson + L1), dense initialisation, anisotropy and isolation pruning **on**; scale cap, pseudo-views and early stopping **off**; all remain switchable in the inspector. `TrainingConfiguration.defaultRegularizers` holds the set, `EarlyStoppingPolicy.offByDefault` the early-stopping default. Stored revision-2 manifests keep what they stored.

Open: pseudo-views losing against the depth prior alone is unexplained (design weakness or a bug, not investigated); the 4-view synthetic regression of the depth prior is unexplained; the benchmark workflow (`.github/workflows/benchmark.yml`) has never run on GitHub.
